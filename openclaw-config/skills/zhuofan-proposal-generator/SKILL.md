# 智能方案初稿生成（ZX-01）

基于用户需求，自动生成符合卓繁信息集团标准的解决方案初稿。定位是「建议型初稿」——供顾问修改完善，不替代核心方案决策。

## 与 official-doc-writer 协同规则

本 Skill 负责「方案内容生成」：需求解析、方案结构、业务逻辑、政策/产品/案例引用、人工审核提示。

`official-doc-writer` 负责「正文排版参考」：Word 版面、字体字号、标题层级、正文缩进、页边距等，生成 `.docx` 时参考其 GB/T 9704-2012 公文正文规范，但不使用正式公文的红色发文机关版头、红线、发文字号和版记。

协同方式：

- 当用户要求生成数字政府方案、项目方案、汇报方案、解决方案初稿时，优先激活本 Skill。
- 本 Skill 不把任务转交给 `official-doc-writer` 重新写内容，避免七章方案结构被改写为普通通知/报告/函。
- 在生成 Word 文档时，使用本 Skill 的 `scripts/generate_docx.py`，该脚本参考 `official-doc-writer` 设置页面、字体、行距、缩进和标题层级，但保持“方案初稿”文档形态。
- 如需确认具体公文格式要求，可查阅 `../official-doc-writer/references/GBT_9704-2012_党政机关公文格式.md`。
- 如果用户明确要求“正式公文”“通知/报告/请示/函”等法定公文，而不是方案初稿，则应使用 `official-doc-writer`。

## 触发条件

以下任一情况时激活此 Skill：

- 用户要求写方案、生成方案、出方案初稿
- 用户提到具体项目需求（如"一网统管方案"、"数据共享平台方案"）
- 用户发送招标文件、采购需求文件要求生成响应方案
- 用户发送需求截图或聊天记录截图要求整理成方案
- 用户提到客户单位类型（数据局、政务中心、大数据中心等）并要求方案输出

## 不适用场景

- 用户只是问政策法规问题（走 ZX-03 政策检索）
- 用户只是查资料、找文件（走 ZX-04 知识库助手）
- 用户要做 PPT（走 ZX-05）
- 用户要做投标文件响应（走 ZX-02）
- 日常闲聊、非方案类工作

## 处理流程

必须按以下流水线顺序执行，不得跳过联网检索、产品/案例匹配和质检审稿：

```
需求解析
→ Tavily 联网检索政策/案例/行业资料
→ 产品库/案例库匹配
→ 生成初稿 JSON
→ 自动质检审稿
→ 修正 JSON
→ Word 输出
```

### 第一步：需求解析

从用户输入中提取以下结构化信息：

| 字段 | 说明 | 示例值 |
|------|------|--------|
| 客户类型 | 数据局 / 政务中心 / 大数据中心 / 数据集团 / 企业 / 其他 | 数据局 |
| 区域 | 省/市/区 | 江西省南昌市 |
| 行业 | 数字政府 / 水务 / 交通 / 航空 / 港口机械 / 其他 | 数字政府 |
| 核心需求 | 一网统管 / 数据共享 / 政务服务优化 / 数据治理 / 其他 | 一网统管 |
| 文档类型 | 解决方案初稿 / 建设情况汇报 / 成效汇报 / 阶段总结 | 解决方案初稿 |
| 关键词 | 从需求中提取的关键技术/业务词 | ["城市运管", "事件协同"] |
| 招标文件 | 是否附带招标/采购文件 | 有/无 |

**信息不完整时必须追问。** 使用以下模板：

```
收到需求。为了生成更贴合的方案，请补充以下信息：
1. 客户是哪个单位？（数据局/政务中心/大数据中心/企业/其他）
2. 哪个城市或区域？
3. 核心需求是什么？（一网统管/数据共享/政务服务优化/数据治理/其他）
4. 有招标文件吗？可以直接发给我
```

**追问规则：**
- 至少需要「客户类型 + 区域 + 核心需求」三项才能开始生成
- 如果用户说"帮我写个方案"但没给任何信息，必须追问
- 如果用户给了招标文件，从文件中提取信息，缺失部分再追问
- 追问最多一轮，避免反复打扰

### 第二步：Tavily 联网检索政策/案例/行业资料

确认信息充分后，先进行联网检索，不得直接开始写正文。

检索对象：

- 政策依据：国家、省级、市级、主题政策。
- 行业资料：白皮书、标准规范、主管部门统计、权威研究报告。
- 成功案例：同类城市、同类客户、同类建设主题案例。

执行要求：

- 优先使用 Tavily 或当前环境可用的联网检索能力。
- 每类资料都必须拆成短 query 检索。
- 每一个拟写入方案的成功案例，都必须单独检索案例名称或“城市 + 主题 + 案例”。
- 检索结果必须记录到 `policy_sources`、`industry_sources`、`cases`。
- 检索失败时才能降级为 `[待联网核验]`，不得把模型记忆写成已核验来源。

### 第三步：产品库/案例库匹配

根据需求关键词、客户类型和建设内容匹配公司产品与案例。

执行要求：

- 当产品库可用时，必须先查产品库，再写 `modules[].product` 和 `ref_products`。
- 当案例库可用时，必须先查案例库，再补充 `cases`。
- 产品库不可用或无法确认产品能力时，标注 `待确认`，不得虚构产品名称或产品能力。
- 案例库不可用时，必须使用联网检索补足案例来源；联网也失败时，才允许写待核验案例。

### 第四步：生成初稿 JSON

**确认信息充分后**，先判断文档类型，再生成结构化 JSON 草稿。

本步骤只生成结构化 JSON 草稿，不直接输出 Word。JSON 草稿必须包含正文内容、政策来源、行业资料来源、案例来源、产品匹配、人工审核提示和生成说明。

#### 文档类型路由

- 用户要求“解决方案、建设方案、项目方案、方案初稿、投前方案”时，使用“七章解决方案结构”。
- 用户要求“建设情况汇报、工作汇报、成效汇报、阶段性总结、建设成效、汇报材料”时，使用“建设情况汇报结构”，不得硬套七章解决方案。
- 如果用户同时提到“方案”和“汇报”，以用户最终交付物为准；如表述不清，追问“是要建设方案，还是建设情况汇报材料？”。

#### 七章解决方案结构（适用于建设方案/项目方案）

```
标题：《{项目名称}》解决方案（初稿）

元信息：
  编制单位：卓繁信息集团
  目标客户：{客户单位名称}
  客户类型：{客户类型}
  编制日期：{当前日期}
  版本：V0.1

一、现状分析
  1.1 政策背景
      引用国家及省市相关政策，每条标注政策名称、发文单位、发文时间。
      按需求匹配引用：数字中国建设整体布局规划、国务院关于加强数字政府建设的指导意见、
      全国一体化政务大数据体系建设指南、数据二十条、十四五政务信息化规划、
      以及对应省市的地方政策。不得固定套用，必须与项目主题和建设内容相关。
  1.2 现状概述
      客户当前信息化建设现状，基于行业通用情况描述。
  1.3 痛点问题
      3-5 个核心痛点，使用"一是……二是……三是……"句式。
      痛点必须与后续「建设内容」一一对应。

二、建设目标
  2.1 总体目标
      一段话概述 + 可量化指标（效率提升比例、覆盖率等）。
  2.2 分项目标
      与 1.3 痛点一一对应，每个痛点对应一个建设目标。

三、建设内容
  3.1 ~ 3.N 分模块描述
      每个模块包含：
      - 功能描述（做什么、解决什么问题）
      - 【产品匹配】标注对应的卓繁产品/能力模块
      - 如无匹配产品，标注「待确认」

四、技术架构
  4.1 总体架构
      采用"五层两体系"标准描述：
      基础设施层 → 数据资源层 → 应用支撑层 → 业务应用层 → 展示层
      + 安全保障体系 + 标准规范体系
  4.2 技术选型
      列出核心技术组件。有信创要求时标注国产化替代方案。

五、实施计划
  5.1 分期路径
      按一期/二期/三期描述，每期包含：建设内容、时间周期、交付物。
  5.2 项目组织
      项目管理架构建议。

六、预算框架
      表格形式，包含：模块名称、建设内容摘要、金额（标注"待定"）。

七、亮点与预期效益
  7.1 方案亮点 — 3~5 个差异化亮点
  7.2 预期效益 — 量化指标（效率提升、覆盖率、成本节约等）
  7.3 成功案例 — 同类项目案例，必须标注来源链接；没有链接时标注 `[待联网核验]`

附录A：人工审核提示
  列出需要人工重点确认的内容：
  - 政策引用是否准确
  - 产品匹配是否正确
  - 预算金额需填写
  - 创新点需人工设计
  - 客户承诺与报价需确认

附录B：生成说明
  - 参考方案来源（如有知识库检索结果）
  - 匹配产品清单
  - 引用政策数量
  - 内容来源说明（来源清单 + 模型辅助生成说明，不做无依据比例估算）

附录C：来源清单
  统一列出政策、行业资料、成功案例的名称、发布单位、时间、来源链接和核验状态。
```

#### 建设情况汇报结构（适用于成效型/汇报型材料）

专家写法参考：不写成“要建设什么”的方案，而写成“已经怎么建、取得什么成效、下一步怎么做”的汇报材料。

```
标题：关于{项目名称}建设情况的汇报

开篇总述：
  交代建设背景、标准/政策依据、建设主线、覆盖范围和总体成效。

一、建设总体概况
  写清建设思路、覆盖范围、已建系统/终端/场景、服务人次、压缩时限、满意度等核心指标。

二、场景建设成效
  按场景分节，每个场景采用：
  场景名称：一句话亮点标题
  概述段：说明该场景解决什么问题、实现什么转变。
  一是……：具体建设做法 + 系统能力 + 量化成效。
  二是……：具体建设做法 + 系统能力 + 量化成效。
  三是……：具体建设做法 + 系统能力 + 量化成效。

三、下一步工作计划
  使用“一是、二是、三是、四是”写后续深化方向，强调场景拓展、体系覆盖、数据赋能、标准规范、运营优化。

结尾：
  总结阶段性成效，承认仍有提升空间，表态持续迭代完善并服务数字政府/营商环境/高质量发展大局。

附录A：人工审核提示
附录B：生成说明
附录C：来源清单
```

建设情况汇报写作要求：

- 每个场景都要体现“业务动作 + 系统能力 + 量化结果”，避免只写功能清单。
- 优先使用“推动……由……向……转变”“构建……体系”“实现……闭环”等成效型表达。
- 可使用标准、政策作为背景依据，但来源仍统一进入附录C。
- 不写预算框架，除非用户明确要求。
- 不写“产品匹配”显性标签，除非用户明确要求内部方案稿。
- 若量化数据没有来源或用户未提供，必须标注待确认，不得编造。

#### 写作规范

**语言风格：**
- 政府公文风格，语言严谨精炼
- 多用"统筹推进"、"深化应用"、"集约建设"、"数据赋能"等术语
- 使用"总-分"结构，层次分明
- 序数词使用"一是、二是、三是"或"（一）（二）（三）"

**针对不同客户类型的侧重点：**

| 客户类型 | 写作侧重 |
|---------|---------|
| 数据局/政务办 | 站位高，讲政治讲成效，突出降本增效、数据共享、基层减负、营商环境优化，用量化数据 |
| 规划方案/可研 | 注重顶层设计，技术路线清晰，投资估算合理，风险可控，信创要求标注国产化 |
| 数据集团/业主 | 强调落地性、可操作性、投资回报率，商业模式设计，分期实施路径 |
| 企业 | 聚焦业务价值、效率提升、成本节约，少讲政策多讲场景 |

**去 AI 化处理：**

生成内容必须检测并消除以下 AI 痕迹：
- 删除："综上所述"、"总而言之"、"值得注意的是"、"不可否认"
- 删除："全方位保障"、"一站式服务"、"赋能千行百业"
- 删除："作为AI"、"我是AI语言模型"、"仅供参考"
- 替换泛化表述为具体数据或场景描述
- 确保每段有实质内容，不堆砌空话

**逻辑一致性检查：**
- 痛点（一章）→ 建设目标（二章）→ 建设内容（三章）必须一一对应
- 建设内容中的产品必须是公司实际有的产品（无法确认时标注"待确认"）
- 政策引用必须有来源链接，不确定的标注"待人工补充"
- 成功案例必须有来源链接，不得只写"公开信息/行业案例"；未检索到链接时必须标注 `[待联网核验]`

### 联网检索与失败降级规则

生成方案前，必须优先查阅并遵守：

```
references/policy-web-search.md
```

凡是要作为方案引用依据的政策、行业资料、统计数据、标准规范、成功案例，只要当前环境具备联网检索能力，就必须先联网检索或查知识库，不得直接凭模型记忆写成已引用依据。调用 `web_search` / Tavily 等联网检索能力时，必须遵守以下规则：

- 如果 `web_search` 返回 timeout、failed、error、no results，视为本次联网检索未成功。
- 检索未成功时，不得声称“已检索到”“根据最新政策”“根据江西省/杭州市某政策”等。
- 检索未成功时，不得编造具体政策名称、发文单位、发文时间、文号或链接。
- 检索未成功时，政策背景只能写通用判断，并显式标注 `[待联网核验]` 或 `[待人工补充]`。
- 只有当搜索结果中能够明确识别政策名称、发文单位、发文时间、来源网站/链接时，才可以作为正式政策依据写入方案。
- 正文不得内嵌 `[来源：...]`、URL 或长链接；所有政策、行业资料、案例来源统一写入“附录C：来源清单”。
- 搜索结果来自新闻稿、转载稿、公众号、媒体报道时，只能作为辅助线索，来源清单中状态必须标注 `待核验原文`，不得当作政策原文。
- 优先引用 `gov.cn`、国家部委官网、省/市政府官网、省/市数据局或政务服务主管部门官网。
- 不得使用一次性长 query 检索政策，必须按“国家政策 / 省级政策 / 市级政策 / 主题政策”拆成短 query。
- 附录B“生成说明”中必须写明政策检索状态：成功、部分成功或失败降级。
- 行业资料、统计数据、标准规范同样必须先联网检索或查知识库。可引用行业白皮书、主管部门统计、权威研究报告、标准规范、公开案例库等，来源写入 `industry_sources`；检索失败时不得编造名称、机构、时间或链接。
- 成功案例必须先联网检索或查知识库，不得直接凭模型记忆填写“公开信息/行业案例”。案例来自政府官网、运营单位官网、权威媒体或公开案例库时，链接写入来源清单；只检索到二手材料时状态写 `待核验原文`；检索失败或没有链接时才允许标注 `[待联网核验]`。

案例检索建议按“项目名 / 城市 + 主题 / 主管单位 + 主题”拆成短 query，例如：

```
成都市 微网实格 社会治理 平台
莆田市 全市一张图 大数据 云平台
上海 城市运行 一网统管 案例
```

如果案例检索失败，不得写成已核验案例；附录C中必须写明状态为 `待联网核验`，交付说明中提示“案例来源待核验”。

执行要求：

- 生成政策依据前，至少执行国家/省市/主题政策检索。
- 生成行业资料或统计判断前，至少执行主题资料检索。
- 生成每一个成功案例前，必须对该案例名称或“城市 + 主题 + 案例”执行检索。
- 未执行检索时，不得把任何政策、资料或案例写成已核验来源。
- 检索失败可以降级，但必须在附录B或交付说明中写明失败降级状态。

推荐将政策检索拆成短查询，避免一次性长 query 导致超时。例如：

```
site:jiangxi.gov.cn 数字政府 建设 政策
site:jiangxi.gov.cn 政务服务 标准化 便利化
site:jxzwfww.gov.cn 政务服务 大厅 智能化
site:gov.cn 数字政府建设 指导意见
```

当政策检索失败时，正文示例：

```
国家和地方持续推进数字政府、政务服务标准化便利化、公共数据共享等工作，为本项目建设提供了总体方向支撑。相关国家及江西省具体政策文件需进一步联网核验后补充。[待联网核验]
```

### 第五步：自动质检审稿

生成初稿 JSON 后，必须按 `references/quality-checklist.md` 进行一次自动质检审稿。

审稿重点：

- 结构完整性：七章、附录A/B/C是否齐全。
- 逻辑一致性：痛点、目标、建设内容是否一一对应。
- 政策贴合度：政策是否与项目主题相关，是否机械套用。
- 来源追溯：政策、行业资料、成功案例是否有链接或核验状态。
- 产品真实性：产品能力是否来自产品库或已标注待确认。
- 案例真实性：案例是否执行联网检索或案例库检索。
- 语言质量：是否存在 AI 套话、空话、夸大承诺。
- 风险控制：预算、客户承诺、量化指标是否需要人工确认。

质检结果必须形成 `review_notes`，写入 JSON 的 `sections.review_notes`。

### 第六步：修正 JSON

根据自动质检审稿结果修正初稿 JSON。

修正规则：

- 发现政策、案例、行业资料缺来源时，优先补检索；仍无法核验时标注 `[待联网核验]`。
- 发现产品能力无法确认时，改为 `待确认`，并写入人工审核提示。
- 发现痛点、目标、模块不对应时，调整章节内容保持一一对应。
- 发现 AI 套话或空泛表述时，改为具体业务动作、系统能力和预期效果。
- 发现预算或量化成效无依据时，改为待确认或建议指标，不做确定承诺。

完成修正后，才允许进入 Word 输出。

### 第七步：生成 Word 文档并交付

**方案内容生成完毕后，必须输出为 .docx 文件。不要直接在对话中贴出全文。**

#### 生成流程

1. 使用已修正的 JSON 作为最终输入
2. 调用 `scripts/generate_docx.py` 脚本生成 Word 文件，版式参考 `official-doc-writer` 公文格式
3. 将 .docx 文件发送给用户
4. 在对话中只发送简要的交付说明（不贴方案全文），必须包含本次生成用时

## 约束与红线

### 绝对禁止

1. **编造政策法规** — 不确定的政策标注「待人工补充」，不得虚构政策文号或内容
2. **虚构产品能力** — 公司没有的产品不得写入方案，不确定的标注「待确认」
3. **上传敏感数据** — 政府项目及内部项目数据严禁上传公开大模型
4. **替代核心决策** — 方案创新点、客户承诺、报价策略必须提醒人工确认
5. **给出具体报价** — 预算栏统一标注"待定"，不做金额承诺
6. **使用 AI 套话** — 见上方「去 AI 化处理」清单

### 来源追溯规则

正文不得内嵌 URL、长链接或 `[来源：...]` 标记。政策、行业资料、成功案例的名称、发布单位、时间、来源链接和核验状态统一写入“附录C：来源清单”。

允许在正文中保留必要的短状态标记：
- `[待联网核验]` — 本次未能核验原文或未提供来源链接
- `[待人工补充]` — 需要顾问补充确认
- `[待确认]` — 产品、客户现状、量化指标等无法确认

### 数据安全

- 用户发送的招标文件、项目信息视为保密信息
- 不在对话中泄露其他客户的项目细节
- 不将客户数据用于非本次方案的其他用途

## 知识库检索指引

当知识库（ChromaDB）可用时，按以下优先级检索：

1. **历史方案库** — 按行业 + 客户类型 + 关键词语义匹配最相似方案，取 Top 3
2. **产品能力清单** — 匹配需求关键词对应的公司产品模块
3. **政策法规库** — 按区域 + 行业检索相关国家/省市政策原文
4. **成功案例库** — 匹配同类项目案例的亮点和量化效益
5. **标准模板** — 按客户类型选择对应方案模板结构

检索结果融入 Prompt 时的格式：

```
【参考历史方案】（来自知识库，相似度排序）
{similar_proposals}

【可用产品模块】（来自产品清单）
{matched_products}

【相关政策法规】（来自政策库）
{relevant_policies}

【成功案例】（来自案例库）
{matched_cases}
```

**当知识库尚未搭建时：**
- 基于模型自身知识生成内容
- 在附录B“内容来源说明”中注明"当前未接入知识库，其余内容为模型辅助生成，请重点审核准确性"
