# 方案材料生成作业流程

本文件只控制通用作业流程，不维护任何具体交付物的标题、章节、字段或质检细则。具体规则必须根据 `document_type` 路由到对应 reference。

## 一、输入理解

先从用户材料中提取：

- 客户单位、区域、客户类型或业务领域；
- 项目名称、核心需求、项目阶段；
- 输入材料类型，如会议纪要、沟通记录、需求截图、任务材料、历史方案；
- 用户明确要求生成的交付物；
- 用户明确要求写入或禁止写入的内容。

处理原则：

- 用户明确说出的客户、区域、交付物类型和写作口径优先。
- 缺少关键上下文且无法从材料判断时，必须追问。
- 客户类型缺失时标注待确认；如材料明显指向某类客户，可基于材料推断并标注依据。
- 用户同时提到多个可能交付物且用途不清时，先追问最终用途。

## 二、交付物路由

需求解析后读取 `../routing/proposal-routing.md`，得到 `document_type`。

处理原则：

- `document_type` 是后续结构、写作、质检和输出处理的总开关。
- 不得只根据材料类型、交付动作或时间要求判断交付物类型。
- 当前 Skill 暂未支持的交付物类型，应先追问或说明暂不展开，不得套用其他类型结构。

## 三、历史资产复用

历史资产复用是可扩展能力。当前只处理用户提供或当前可用材料中的历史方案；后续如接入外部检索或材料召回能力，也在本步骤统一处理。

复用时必须形成 `historical_asset_review`。

允许复用：

- 客户背景、区域特点、既有基础；
- 成熟的章节组织方式和顾问表达；
- 已脱敏、可迁移的产品能力和案例表达。

禁止复用：

- 其他客户专属数据、金额、周期、内部信息；
- 与本次需求无关的内容模块；
- 未经本次核验的历史政策依据；
- 历史项目中的承诺性成效。

## 四、资料检索与核验

资料检索按需执行。需要把政策、行业资料、统计数据、标准规范、产品能力或案例写入材料时，读取 `../search/source-web-search.md`。

处理原则：

- 写入材料作为依据或事实支撑的内容必须有来源或核验状态。
- 检索失败时记录失败原因，并标注 `待联网核验` 或 `待核验原文`。
- 不需要引用的内容，不为了满足流程强行检索。
- 检索和核验记录写入对应 `document_type` 要求的来源字段；没有要求时，至少进入 `sections.source_note` 或 `sections.review_notes`。

## 五、内容映射

内容映射规则按 `document_type` 对应结构文件执行。

通用要求：

- 用户材料中的关键需求必须能映射到输出材料中的对应内容。
- 交付物内容、产品能力、来源依据、预期价值和待确认项之间应能互相对应。
- 产品或能力无法确认时写 `待确认`。
- 量化成效没有来源时，只能写为建议指标或待测算指标。

具体结构文件由 `../routing/proposal-routing.md` 中的路由结果决定。

## 六、写作与润色

写作和润色规则读取 `../writing/consultant-writing-rules.md`。

具体章节、标题、内容边界和写作重点由 `document_type` 对应结构文件决定。

## 七、质检修正

输出前读取 `../routing/quality-routing.md`，根据 `document_type` 选择质检清单。

处理原则：

- 只读取当前 `document_type` 对应的 checklist。
- 质检发现的问题必须先修正 JSON，再进入输出环节。
- `sections.review_notes` 应记录需要人工审核、待核验或待补充的事项。

## 八、最小中间产物

进入输出环节前，至少形成以下结构：

```json
{
  "document_type": "",
  "requirement_parse": {},
  "historical_asset_review": [],
  "content_mapping": [],
  "sections": {
    "review_notes": [],
    "source_note": ""
  }
}
```

其他字段由 `document_type` 对应结构和生成器决定。
