# 项目汇报生成作业流程

本文件控制 ZX-01 当前阶段的作业流程。当前阶段只生成项目需求阶段的项目汇报稿/项目建议支撑材料，目标是把用户材料整理成可复核、可追溯、便于顾问继续修改的建议型初稿。

## 一、输入理解

先从用户材料中提取：

- 客户单位、区域、客户类型或业务领域；
- 项目名称、核心需求、项目阶段；
- 输入材料类型，如会议纪要、沟通记录、需求截图、任务材料、历史方案；
- 用户明确要求生成的交付物；
- 用户明确要求写入或禁止写入的内容。

处理原则：

- 用户明确说出的客户、区域、交付物类型和写作口径优先。
- 缺少区域和核心需求且无法从材料判断时，必须追问。
- 客户类型缺失时标注待确认；如材料明显指向某类客户，可基于材料推断并标注依据。
- 用户同时提到“方案”和“汇报”且用途不清时，先追问最终用途。

## 二、交付物判断

需求解析后读取 `../routing/proposal-routing.md`。

- 如果路由为 `project_report`，继续当前流程。
- 如果路由为其他类型，先追问或说明当前阶段暂不展开该交付物。
- 不得仅凭“会议纪要”“生成材料”“做成 Word”“下周要方案”等材料类型或交付动作判断为项目汇报。

## 三、历史资产复用

读取用户提供或当前可用材料中的历史方案后，形成 `historical_asset_review`。

允许复用：

- 客户背景、区域特点、既有建设基础；
- 成熟的章节组织方式和顾问表达；
- 已脱敏、可迁移的产品能力和案例表达。

禁止复用：

- 其他客户专属数据、金额、周期、内部信息；
- 与本次需求无关的建设模块；
- 未经本次核验的历史政策依据；
- 历史项目中的承诺性成效。

## 四、必要资料检索

需要把政策、行业资料、统计数据、标准规范或案例写入材料时，读取 `../search/policy-web-search.md`。

处理原则：

- 写入材料作为依据或事实支撑的内容必须有来源或核验状态。
- 检索失败时记录失败原因，并标注 `待联网核验` 或 `待核验原文`。
- 不需要引用的内容，不为了满足流程强行检索。
- 所有检索和核验过程写入 `sections.search_log`。

## 五、内容映射

生成内容前形成 `content_mapping`，至少覆盖：

```text
用户材料
→ 业务问题
→ 建设目标
→ 建设内容
→ 产品或能力支撑
→ 政策或资料依据
→ 预期价值
→ 待确认项
```

要求：

- 每个业务问题应对应建设目标和建设内容。
- 每项建设内容说明服务对象、事项范围、服务渠道或应用场景。
- 产品或能力无法确认时写 `待确认`。
- 量化成效没有来源时，只能写为建议指标或待测算指标。

## 六、结构与写作

项目汇报结构读取 `../structures/project-report.md`。

写作和润色读取 `../writing/consultant-writing-rules.md`。

当前阶段项目汇报稿重点服务项目需求沟通、内部评审、立项论证或客户汇报。具体章节和内容边界按 `../structures/project-report.md` 执行。

## 七、质检修正

输出前读取 `../routing/quality-routing.md`，根据 `document_type` 选择质检清单。

当前阶段路由为 `project_report` 时，使用 `../quality/project-report-checklist.md`。

质检发现的问题必须先修正 JSON，再生成 Word。

## 八、最小中间产物

生成 Word 前，至少形成以下结构：

```json
{
  "requirement_parse": {},
  "historical_asset_review": [],
  "content_mapping": [],
  "sections": {
    "review_notes": [],
    "search_log": [],
    "stage_timings": {},
    "source_note": ""
  }
}
```
