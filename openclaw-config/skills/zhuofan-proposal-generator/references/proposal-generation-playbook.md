# 方案初稿生成作业规程

本文件定义 ZX-01 在新需求场景下的专家化工作流程。目标不是复刻某个历史案例，而是把“用户需求 + 历史方案资产 + 主动联网检索”加工成可复核、可追溯、接近资深顾问水平的方案初稿、汇报材料或 PPT 大纲。

## 一、输入与来源

### 1.1 用户需求源

用户需求源是最高优先级，包含：

- 一句话需求、项目名称、关键词；
- 会议纪要、聊天记录、需求截图；
- 招标文件、采购需求、评分表；
- 用户明确指定的客户、区域、交付物类型和写作口径。

处理原则：

- 用户明确说出的客户、区域、交付物类型不得被历史方案或通用模板覆盖。
- 口语化需求必须转写为“业务问题、建设任务、系统能力、应用场景、预期价值”。
- 缺少区域和核心需求时必须追问；缺少客户类型时可默认政务服务中心，并标注待确认。

### 1.2 历史资产源

历史资产源用于补充客户背景、既有建设基础、成熟表达和可迁移经验，包含：

- 同客户历史方案；
- 同区域历史方案；
- 同主题历史方案；
- 公司产品能力、案例描述、过往标书或汇报材料。

处理原则：

- 历史方案只能作为参考资产，不得直接替代新需求。
- 优先复用客户背景、区域特点、既有基础、章节组织方式和成熟表述。
- 不得复用其他客户专属数据、金额、实施周期、承诺指标和与新需求无关的建设模块。
- 如历史方案与用户新需求冲突，以用户新需求为准，并将冲突写入待人工确认项。

### 1.3 外部检索源

外部检索源由 Skill 主动通过 Tavily、百度、政府网站或当前可用联网检索工具获取，不要求用户预先提供政策文件。

必须主动检索：

- 国家级政策；
- 省市级政策；
- 区县级政策；
- 主题专项政策；
- 行业资料、标准规范、统计数据；
- 可公开引用的同类案例。

处理原则：

- 外部来源必须写入 `search_log`、`policy_sources`、`industry_sources` 或 `cases`。
- 没有成功检索或没有来源链接时，不得写成“已依据”“已核验”。
- 新闻稿、公众号、转载页只能作为线索，不能替代政策原文。
- 检索失败必须区分 `failed`、`no_results`、`partial`、`not_run`，并在交付说明或附录B中说明降级原因。

## 二、总流程

每次生成前按以下流程执行：

```text
需求解析
→ 交付物类型判断
→ 历史资产召回与可复用内容筛选
→ Tavily/百度/政府网站检索政策、行业资料和案例
→ 来源可信度筛选
→ 需求到建设内容映射
→ 成品结构设计
→ 专家化正文生成
→ 自动质检与修正
→ Word/PPT/文本输出
```

不得跳过“历史资产筛选、外部检索、内容映射、质检修正”直接套模板写正文。

## 三、需求解析规程

### 3.1 必须抽取的字段

- 客户单位；
- 客户类型；
- 区域层级；
- 行业领域；
- 核心需求；
- 交付物类型；
- 项目阶段；
- 目标用户；
- 服务渠道；
- 事项范围；
- 关键词；
- 用户明确不要写或必须写的内容。

### 3.1.1 交付物类型优先路由

先读取 `proposal-routing.md` 判断交付物类型，再进入正文结构设计。

路由后只读取对应结构文件：

- `project_report`：`structures/project-report.md`
- `solution`：`structures/solution-draft.md`
- `achievement_report`：`structures/achievement-report.md`

不得在本文件重复维护具体路由细则和章节模板。

### 3.2 需求转写规则

将原始表达按以下链路转写：

```text
原始需求
→ 真实业务问题
→ 建设任务
→ 系统能力
→ 应用场景
→ 预期成效
→ 待确认边界
```

示例规则：

- “想做政策平台”不能直接写成“建设政策平台”，应拆成政策查询、政策匹配、主动推送、申报辅导、政策兑现、运营分析等业务能力。
- “要智能帮办”不能只写智能问答，应结合目标用户、办理事项、服务渠道和人工窗口协同方式。
- “参考历史方案”不能默认沿用历史建设内容，应先判断本次需求是否同客户、同区域、同主题、同阶段。

### 3.3 追问闸门

必须追问的情况：

- 无区域且无法从材料判断；
- 无核心需求且无法从材料判断；
- 无法判断最终交付物是方案、汇报、PPT、采购需求还是投标辅助材料。

最多追问一轮。用户仍未补充时，可基于可用材料生成，但必须标注假设和待确认项。

## 四、历史方案复用规程

### 4.1 先判定相似度

读取历史方案后，先判断四类相似度：

| 维度 | 判断问题 | 使用方式 |
|---|---|---|
| 客户相似 | 是否同一客户或同类客户 | 可复用客户背景和服务对象 |
| 区域相似 | 是否同一区域或同层级区域 | 可复用区域政策口径和地方特色 |
| 主题相似 | 是否同一建设主题 | 可复用模块结构和痛点表达 |
| 阶段相似 | 是否同为投前、汇报、深化或投标 | 可复用交付物结构 |

### 4.2 可复用内容

允许复用：

- 客户已有建设基础；
- 地方服务品牌、平台名称、改革方向；
- 成熟章节结构；
- 已验证的业务场景拆分；
- 通用产品能力表述；
- 可公开引用且已脱敏的案例表达；
- 专家化句式和段落组织方式。

### 4.3 禁止直接复用内容

禁止直接复用：

- 其他客户名称、专属数据和内部信息；
- 未确认的服务量、金额、建设周期、人员配置；
- 与新需求无关的系统模块；
- 历史项目的承诺性成效；
- 历史方案中的政策依据，除非本次重新检索或能核验仍适用。

### 4.4 历史资产输出要求

生成正文前应形成“历史资产复用说明”，至少包含：

- 读取了哪些历史方案；
- 每个历史方案可复用的内容；
- 被排除的内容及原因；
- 与新需求存在冲突或需确认的内容。

## 五、外部检索规程

外部检索按 `policy-web-search.md` 执行，本文件只规定生成前的业务目标。

### 5.1 检索顺序

1. 国家级上位政策：用于说明方向和合规依据。
2. 省市级政策：用于说明区域改革要求和主管部门部署。
3. 区县级政策：用于增强本地化贴合度。
4. 主题专项政策：用于支撑具体建设内容。
5. 行业资料与标准规范：用于支撑技术路线、服务规范和指标口径。
6. 同类案例：用于支撑可行性和亮点表达。

### 5.2 检索词生成

检索词必须由需求解析结果生成，不得使用一条长 query 覆盖全部问题。

最小检索矩阵：

- `site:gov.cn {核心需求} 政策`
- `{省/市} {核心需求} 政务服务 政策`
- `{区县} 政府职能转变 行政审批 政务服务`
- `{核心需求} 标准 指南`
- `{区域或同类城市} {核心需求} 案例`

### 5.3 来源筛选

优先级：

1. 政府官网、国务院公报、部委官网；
2. 省市区政府官网、数据局、政务服务主管部门；
3. 标准发布机构、主管部门白皮书；
4. 权威媒体报道；
5. 普通新闻稿或转载页。

第 4、5 类只能作为辅助线索。无法找到原文时，必须标注 `待核验原文`。

## 六、内容映射规程

生成正文前必须形成映射关系，不得直接铺正文。

### 6.1 标准映射链路

```text
用户需求/会议纪要
→ 业务痛点
→ 建设目标
→ 建设模块
→ 产品或能力支撑
→ 政策依据
→ 历史方案参考
→ 预期成效
→ 待确认项
```

### 6.2 建设模块生成规则

每个建设模块必须回答：

- 解决哪个业务问题；
- 面向哪些用户或部门；
- 覆盖哪些事项、渠道或场景；
- 建设哪些系统能力；
- 与历史方案或产品能力的关系；
- 引用哪些政策依据；
- 预期形成什么价值；
- 哪些名称、指标、边界待确认。

### 6.3 产品能力约束

- 产品能力必须来自产品清单、历史方案、案例库或用户材料。
- 无法确认产品名称时，写“能力模块”而不是虚构产品名。
- 不确定的产品映射统一标注 `待确认——需与产品/售前团队核实`。

## 七、交付物结构路由

先判断交付物类型，再选结构。

| 用户目标 | 使用结构 | 写作重点 |
|---|---|---|
| 解决方案、建设方案、方案初稿 | 项目需求阶段解决方案结构 | 为什么做、做什么、边界是什么、价值是什么 |
| 汇报材料、建设情况汇报、成效汇报 | 汇报型结构 | 已做什么、取得什么成效、问题不足、下一步计划 |
| PPT、汇报演示 | PPT 大纲结构 | 先结论、强主线、模块化表达、适合领导阅读 |
| 采购需求 | 采购需求结构 | 建设范围、功能需求、服务要求、验收口径 |
| 投标响应辅助 | 投标辅助结构 | 评分点、响应项、风险项、可复用素材 |

如果用户同时提到“方案”和“汇报”，以最终成品用途为准；无法判断时必须追问。

## 八、专家化写作规程

### 8.1 总体写法

正文不得从模板空泛展开，必须围绕“客户真实问题”组织。

推荐段落逻辑：

```text
政策或业务背景
→ 本地现状或用户痛点
→ 建设必要性
→ 建议建设内容
→ 业务价值和待确认边界
```

### 8.2 模块写法

每个建设模块采用：

```text
模块定位
→ 服务对象
→ 业务流程
→ 核心功能
→ 数据/系统支撑
→ 应用成效
→ 产品匹配或待确认
```

### 8.3 语言要求

- 多写具体业务动作，少写抽象口号。
- 多写“面向谁、在哪个场景、解决什么问题”，少写“打造平台、全面赋能”。
- 政策表达必须和建设内容发生关系，不能只堆政策名称。
- 成效指标没有来源时只能写为“建议关注指标”或“待测算指标”，不得写成确定承诺。
- 不使用“综上所述”“总而言之”“全方位赋能”“一站式服务”等空泛表达，除非它是正式产品名或政策原文。

## 九、质检与修正规程

输出前必须先读取 `quality-routing.md`，再按对应 `document_type` 的 checklist 审稿，并形成 `review_notes`。

重点检查：

- 用户真实需求是否被回应；
- 历史方案是否被合理复用，是否泄露其他客户信息；
- 政策和案例是否有来源台账；
- 痛点、目标、模块、成效是否一一对应；
- 产品能力是否有来源或标注待确认；
- 是否存在编造政策、编造数据、编造案例；
- 是否存在套话、空话和交付物类型错配；
- 待人工确认项是否进入附录A/B/C或交付说明。

质检发现的问题必须先修正 JSON，再生成 Word、PPT 或最终文本。

生成正文前，至少在内部形成以下结构：

```json
{
  "requirement_parse": {
    "customer": "",
    "customer_type": "",
    "region": "",
    "deliverable_type": "",
    "core_requirement": "",
    "target_users": [],
    "service_channels": [],
    "scope": [],
    "assumptions": [],
    "questions_or_confirmations": []
  },
  "historical_asset_review": [
    {
      "file": "",
      "reuse": [],
      "exclude": [],
      "risks": []
    }
  ],
  "search_plan": [
    {
      "category": "",
      "query": "",
      "purpose": ""
    }
  ],
  "content_mapping": [
    {
      "pain_point": "",
      "goal": "",
      "module": "",
      "capability_or_product": "",

      "historical_reference": [],

    }
  ]

```

该中间产物不一定全部展示给用户，但必须支撑最终正文、附录和交付说明。
