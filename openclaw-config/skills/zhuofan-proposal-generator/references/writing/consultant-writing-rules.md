# 顾问写作与润色规则

本文件用于项目汇报稿的内容生成和初稿润色。目标是让材料像顾问写出的项目需求阶段汇报稿，而不是模板拼接或 AI 套话。

## 什么时候使用

- 生成项目汇报内容前，用于确定表达口径。
- 完成内容初稿后，用于润色、压缩和去 AI 化。
- 质检前，用于检查语言是否具体、克制、可复核。

## 写作口径

- 围绕客户真实问题组织内容，不从宏大背景空泛展开。
- 优先写清楚“为什么建、准备建什么、依据是什么”。
- 多写具体业务动作、建设事项、服务对象、系统或数据关系。
- 少写抽象口号、泛化价值和无法核验的效果承诺。
- 不把项目汇报写成完整技术方案、实施方案、预算方案或投标响应。

## 段落要求

- 每段只表达一个核心观点。
- 先写事实、依据或问题，再写建议建设内容和价值。
- 会议纪要或需求材料中已有的明确事项，应优先转写为正式表达。
- 没有来源的数据、指标和成效，只能写成建议关注指标或待测算指标。
- 对待确认的客户名称、系统名称、指标、范围和产品能力，应显式标注待确认。

## 润色规则

- 删除重复表达、无关修饰和空泛过渡句。
- 将口语化表达转成正式项目材料表达。
- 长段落拆成短段或条目，便于顾问复核。
- 保留具体建设动作，不为了显得高级而堆叠术语。
- 政策、案例、产品能力等来源不清时，不写成已核验事实。

## 禁用表达

| 类型 | 禁用表达 | 处理方式 |
|---|---|---|
| 开头套话 | 在当今数字化转型的浪潮中 | 直接切入项目背景或需求 |
| 结尾套话 | 综上所述、总而言之 | 删除，直接写判断或建议 |
| 万能形容 | 全方位、一站式、全面赋能 | 改成具体功能、对象或场景 |
| 夸大承诺 | 显著提升、大幅降低、全面优化 | 无依据时改为建议目标或预期方向 |
| 身份暴露 | 作为 AI、我是语言模型 | 删除 |
| 机械排比 | 连续多个“通过……实现……” | 合并为具体建设动作 |

## 输出前自检

- [ ] 是否回应了用户提供的真实需求。
- [ ] 是否围绕项目需求阶段汇报，而不是完整解决方案展开。
- [ ] 是否避免了套话、空话和无法核验的承诺。
- [ ] 是否保留了来源、待核验和待确认提示。
- [ ] 是否便于顾问继续修改和补充。
