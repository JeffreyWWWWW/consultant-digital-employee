# 项目汇报质量检查清单

适用于 `document_type: "project_report"`。

## 结构与标题

- [ ] 标题直接写材料标题，不加书名号《》。
- [ ] 标题不得包含“解决方案”“解决方案（初稿）”“（初稿）”。
- [ ] 标题应体现客户单位、项目名称和“汇报”。
- [ ] 正文主体只包含“项目建设的依据、建设目标、建设内容”三类内容。
- [ ] 文末保留“附录A：政策与资料来源链接”和“附录B：需人工审核事项”。
- [ ] 未默认生成技术架构、成功案例、预算、实施计划、项目组织等方案扩展内容。
- [ ] 文件名使用 `{客户单位}{项目名称}建设项目汇报_{YYYYMMDD}.docx`，不得使用内部过程命名或解决方案初稿命名。

## 政策依据

- [ ] 政策依据围绕项目建设必要性展开，不做泛泛政策背景。
- [ ] 已优先检索国家、省市、区县、主题专项政策。
- [ ] 区县项目体现本地政府职能转变、营商环境、一网通办、人工智能+政务服务、政策精准推送等直接依据。
- [ ] 每条政策说明对本项目的支撑关系。
- [ ] 政策名称、来源机构、文号/发布时间和原文链接或核验状态已进入附录A。
- [ ] 未核验的政策标注 `待核验原文` 或 `待联网核验`，不得写成已核验。

## 建设目标

- [ ] 建设目标来自会议纪要、任务安排、需求清单或用户明确要求。
- [ ] 写清是在什么既有系统或服务基础上升级。
- [ ] 覆盖页面优化、功能完善、移动端适配、政策匹配、数据互联互通等实际目标。
- [ ] 不写“全国领先、标杆示范”等宏大口号，除非用户材料明确要求并标注待确认。

## 建设内容

- [ ] 优先抽取会议纪要、需求清单、历史方案中的具体建设项。
- [ ] 未泛化成标准系统模块或六章解决方案模块。
- [ ] 每项采用“事项名称 + 建设动作 + 业务价值”的写法。
- [ ] 不显式写“产品匹配”标签，除非用户明确要求内部售前方案。
- [ ] 未虚构产品能力、实施周期、金额或承诺性指标。

## 交付说明

- [ ] 最后一条交付说明简洁说明文件已生成。
- [ ] 不在对话中展开材料全文或完整检查清单。
- [ ] 来源链接、待核验内容和人工审核提示已分别写入 Word 文档附录A和附录B。
