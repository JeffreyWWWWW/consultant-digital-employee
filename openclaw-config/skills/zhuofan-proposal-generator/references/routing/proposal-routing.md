# 交付物类型路由

本文件只负责判断本次用户需要的交付物类型。判断完成后，再由当前 Skill 决定是否继续处理。

当前阶段已实现：

- `project_report`：项目需求阶段的项目汇报/项目建议支撑材料。

其他类型只做识别和追问，暂不在当前阶段展开：

- `solution`：完整解决方案、技术方案、建设方案、售前方案等。
- `bid_support`：招投标方案、投标响应辅助、评分点响应材料等。
- `achievement_report`：建设情况汇报、成效汇报、阶段总结等。
- `other_material`：普通会议整理、任务清单、需求文档排版、培训材料等。

## project_report

路由为 `document_type: "project_report"` 后，当前阶段继续处理，结构读取 `../structures/project-report.md`，Word 生成器走 `scripts/docx_generators/project_report.py`。

适用情况：

- 用户明确要求项目汇报、项目建设汇报、项目建议支撑材料、立项依据材料。
- 阶段定位是项目需求阶段。
- 写作目标是说明“为什么建、准备建什么、依据是什么”。
- 材料内容包含项目背景、建设诉求、建设目标、建设内容、系统优化、功能完善、数据对接、页面优化或适配改造等信息。
- 使用场景服务于项目建设沟通、立项支撑或评审支撑。
- 未明确要求完整技术方案、实施方案、预算、项目组织或投标响应。

不能单独作为判定依据：

- 会议纪要、沟通纪要、任务安排、需求文档、聊天记录等材料类型。
- “生成材料”“出个初稿”“整理成 Word”“下周要方案”等泛化交付表达。

不得路由为 `project_report`：

- 只是普通会议整理、沟通记录润色、任务清单、工作安排、需求规格说明、培训材料或汇报演示。
- 无法判断具体方案类型或最终用途。
- 用户明确要求售前方案、完整解决方案、技术方案、建设方案、实施方案、投标方案或可研深化内容。

## 暂不展开的类型

如果判断为 `solution`、`bid_support`、`achievement_report` 或 `other_material`：

- 不继续套用项目汇报结构。
- 优先追问最终用途、交付对象和期望深度。
- 如用户确认不是项目需求阶段项目汇报，说明当前阶段暂不展开该交付物。

## 追问规则

- 无法判断交付物类型时，优先追问最终用途。
- 追问后仍不明确时，不得仅因输入是会议纪要类材料就默认 `project_report`。
- 用户只给泛化交付动作时，应追问“这是项目需求阶段汇报，还是完整方案/投标/总结类材料？”
